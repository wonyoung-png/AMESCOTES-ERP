## 지적

1. 원 작성자만 차단하면 현재 판을 수정한 승인자의 자기 승인 가능. 대표가 작성한 초안을 대표가 승인할 수 없다는 명세는 현재 직원 계정 미등록 상황에서 의도된 차단인지 결정 필요. 이번 구현은 예외를 만들지 않고 차단 유지.
2. 채널 상품 생성 후 is_test·sku·item_id 변경 금지. 실상품에 테스트 표시를 켜 삭제하는 위험.
3. 예약 시각의 미래 검사는 예약 요청 시점에만. 공개 실행·이미 공개된 상품 수정 검증에 적용하면 항상 실패.
4. 승인 시 listing 판 + 실제 품목·이미지·코드표 근거를 함께 묶고 공개 직전 비교. 예약 직전 수정은 재승인.
5. 채널 생성 응답 유실 시 진행중 단계를 먼저 저장하고 SKU/핸들 재조회. 무조건 생성 재시도 금지. lease와 저장 시 소유자 비교 필요.
6. 이미지 자매 복사에서 파일ID 복사 금지. READY 확인 후 연결; 다른 상품 참조가 없을 때만 삭제.
7. 팀명은 서버 app_users.team 기준. 별칭을 임의 허용하지 말고 현재 명세 지정 팀 외 차단.
8. 사이즈 기준표 키 모델명 정규화, 가방의 미확정 사이즈는 차단. 가방 외 품목 면제 여부는 분류 근거로 판단.
9. 카페24 검색 재추가 금지 태그: 빠니에·통근백·데일리백·A4가방. 일본어 제목/SEO 번역 금지, body_html과 product_details만.
10. 재고는 채널 독립. ERP 테스트 입고로 프리오더 자동 해제 금지. CONTINUE에서 한도 감시만으로 정확한 판매한도 보장은 불가능하므로 채널별 통제와 검수 필요.
11. 카페24 태그 반영은 60~90초 지연, 즉시 불일치를 확정 실패로 판단하지 않음.
12. 자사몰관리는 조직도 teamEvidence로 freshness 계산하면 항상 stale. 자체 근거/시간을 사용하고 콘솔 officeAgents 목록과 자체 상태를 유지. 별도 manual runner·잠금. 일일 trigger를 일반 schedule과 분리.
13. RELATED_TEAMS 키 추가만으로 협의가 자동 발생하지 않음. 후보 입력 경로까지 확인 필요. 장기 방치 이슈를 일반 업무카드로 만들면 팀 미지정 에이전트 모델 호출이 생길 수 있으므로 비서실 결정 데이터에 직접 포함하는 방식 권고.
