# 비재무 업무 연결·동시 변경 검증 — 2026-10-10

## 범위와 결정

대표님 지시에 따라 재무 실자료 입력·복원, 법인 원장 분리, 은행 연동, 직원 개방은 보류한다. 이번 실제 HTTP/DB 연결 시험은 업무 입력→팀장 확인→일정 확정→팀 공유→질문·비서실 보고만 실행했다. 금융 라우터를 호출하지 않았고 production_orders/trade_statements/settlements/payables는 최종 0건을 검사했다. 기존 재무 계산·계약의 로컬 대역 회귀시험은 실행했으나 실제 재무 거래를 생성하지 않았다.

## 수정

| 항목 | 변경 |
|---|---|
| 업무 변경 | 답변·종류 변경·취소·완료가 서버에서 읽은 id/status/kind/updated_at 모두 일치할 때만 저장; 충돌 409, 후속 알림 없음 |
| 일정 확정 | DB 행 잠금 후 예상 updated_at 검사; 마이크로초 보존; 구 4인자 함수는 권한 회수와 호출 거부로 우회 차단 |
| 충돌 오류 | SQLSTATE PT409 사용. 초기 40001 구현은 실제 PostgREST 경로에서 지연되어 배포하지 않았고 수정 후 전체 연결 재검증 |
| 잘못된 AI 응답 | 알 수 없는 종류·배열/문자열 parsed를 팀 공유로 전환하지 않고 개인 안내로 처리 |
| 기획전 저장 | 전체 목록 upsert 제거, 변경 행만 id+updated_at 조건 PATCH, 신규 행 INSERT; 동일 브라우저 연속 수정은 승인된 서버 버전으로 직렬 처리 |
| 저장 실패 | 현재 캐시가 해당 제출본일 때만 서버 재조회로 복구; 통신 불가면 승인된 이전본 복원; 오류를 화면에 표시 |
| 일정 조회 | 조회만으로 서버 쓰기·예시 기획전 자동 생성하지 않음; 기존 실자료나 이전 예시 행을 삭제하지 않음 |
| 캘린더 | 상태값으로 재계산; 업무/기획전 변경 및 다른 탭 저장 변경 반영, 리스너 해제; 열린 상세 패널도 최신 행 반영 |
| 챗봇 재시도 | 사용자별 sessionStorage에 원문·요청 ID를 전송 전에 보존; 응답 미확인 상태의 다른 문장 전송 차단; 동일 탭 새로고침 후 같은 ID로 재시도 |

## 증거

- 전체 TypeScript 시험 132건 PASS(격리된 실제 캘린더·챗봇 React 브라우저 시험 포함), MJS 회귀 7파일 PASS, 타입 검사·운영 빌드 PASS.
- 실제 로그인·쿠키/HTTP/PostgREST/PostgreSQL 업무 연결 12검사 그룹 PASS. 최종 `WORK_ONLY_PASS_NO_FINANCE_RUN`, 모델 대역 응답 7회, 확정 20%가 질문 및 두 팀 보고 근거에 포함되는 검사 3회.
- 서버가 읽은 직후 실제 DB에서 종류/담당자/버전을 변경한 강제 경합 6종 PASS: 답변→일정, 완료→일정, 종류변경→확인요청, 취소→확인요청, 완료→동일종류 새담당자, 확정→동일종류 새버전. 오래된 저장 0건·알림 0건.
- 격리 DB SQL: 새 확정 버전·권한 시험 PASS, 기존 일정 확정 회귀 12검사 PASS. 테스트 함수 호출은 새 서명으로 갱신했다.
- 최종 실제 연결 SSM `28b3018b-bc8d-42ed-8ed9-797ddffb64b0`, SQL `dff7853a-0686-45e6-8f84-56c0ff9be55a`. 앞선 중간 실행이나 지연된 실행을 최종 통과 증거로 사용하지 않는다.
- SDK 캠페인 전송 시험은 실제 PostgREST SDK와 fetch 대역으로 조건 PATCH·충돌 후 캐시 복구를 검사했다. 실제 직원 두 세션의 운영 캠페인 수정은 실행하지 않았다.
- Banach/Volta 독립 Codex 검토: 캠페인 동기화, 확정 SQL/호출부, 캘린더·챗봇 보존 경로에 추가 배포 차단 지적 없음. graphify는 관계 탐색 후 현재 소스로 오래된 연결을 교정했고, karpathy-guidelines는 변경 범위와 검증 경계를 제한하는 데 적용했다.

## 운영 적용 조건

원격에 선별 커밋·푸시 후 전역 배포 잠금 아래 앱만 한 번 빌드한다. 기존 함수 정의·권한과 이미지 복구본을 보존하고, 새 함수를 적용한 직후 새 앱을 교체한다. 운영 회사 거래·알림은 만들지 않으며 직원 잠금 `ERP_PRIVATE_MODE=true` 유지, 내부 건강 상태·공개 미로그인 차단을 읽기 전용으로 확인한다. 이 문서의 시험 결과는 운영 로그인 후 전 메뉴 클릭 완료나 실모델 전체 흐름 완료라는 뜻이 아니다.

## 후속 완료 — 당시 결정과 현재 일정 구분

- `confirmed_payload`는 변경하지 않고, 이미 볼 권한이 있는 업무 카드의 `result_ref`로 현재 캠페인을 연결한다. 과거 결정 20%와 현재 할인율 15%·변경 날짜·상태·수정시각을 별도 근거로 제공한다.
- 현재 값/마감, 연결 행 없음, 조회 실패, 연결 정보 없음은 별개다. 행 없음만으로 삭제 사유·시점·취소 여부를 추론하지 않으며 조회 실패를 빈 정상 자료로 처리하지 않는다.
- 현재 미래 일정으로 옮긴 과거 카드도 보완 조회한다. 직원의 카드 권한 필터는 유지하며 공유 팀을 자동 확대하지 않는다. 카드 표본 선정 전에 현재 제목·할인율 근거를 연결한다.
- 팀 보고·직원 질문·협의가 동일 근거 표현과 우선순위를 사용한다. 협의는 원문/답변만 축약해 확정 필드가 잘리지 않도록 했으며, 취소·현재 항목 없음·마감 카드는 신규 업무 협의 후보에서 제외한다. 기존 완료 협의의 자동 재분석은 아직 별도다.
- 회귀 TypeScript 149건·MJS 7파일·타입 검사·빌드 PASS. 질문/팀 보고 프롬프트 12개 시나리오와 연결·절단·권한·보완 조회 helper 5개를 포함한다.
- 실제 격리 HTTP/DB 최종 SSM `54cc6229-8ab1-4add-854c-fcfe66cf0c62` Success: 기본 업무 연결 12그룹·경합 6종 유지, 캠페인 15%·11/20 변경 후 오래된 1월 결정 카드가 질문/마케팅 보고에 포함되고 둘 다 저장됨. 같은 카드 근거 줄에서 당시 20%, 정확한 캠페인 ID, 현재 15%·11/20, 실제 DB 수정시각을 함께 검사했다.
- 모델 10회는 정해진 응답 대역, OAuth는 테스트 서명이다. 실제 모델 판단 품질·운영 인증 화면 전체 클릭·동시 변경 중 원천의 원자적 스냅샷은 검증하지 않았다. 재무 라우터 호출 없이 지정 거래표 4개는 최종 0건 유지.
- 독립 Codex 검토에서 검증식 허점(다른 카드의 현재 값으로 통과 가능)을 지적받아 같은 카드 검사로 수정·새 스택 재검증했다. 추가 배포 차단 지적 없음. 화면 배치 변경 없이 새 질문과 다음 보고/협의 생성의 근거 내용만 달라진다. 기존 저장 보고는 소급 변경하지 않는다.
