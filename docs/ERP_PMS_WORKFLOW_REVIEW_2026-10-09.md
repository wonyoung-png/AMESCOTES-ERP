# ERP·PMS 업무흐름 및 탭 재검토

검토일: 2026-10-09 · 상태: 분석 완료 / 기능 변경·삭제·배포 없음

## 결론

메뉴 수를 먼저 줄이는 것보다 **같은 업무가 여러 저장소에서 서로 다른 상태로 기록되는 문제를 먼저 해결해야 합니다.**

- 통합할 것: 직원 입력창, 리오더 실행, 일정 원본, 상품 식별자, 매출·비용 기준, 승인 대기 진입점.
- 분리할 것: 브랜드 구매와 OEM 수주·생산 책임, 계획과 확정, 영업 분석과 회계 손익, 공유 업무와 대표 전용 비서실.
- 제거할 것: 중복 입력, 동기화 대상 자동 데이터의 자유 편집, 직원 화면의 개발용 동기화 버튼, 실제로 연결되지 않은 화면 코드.
- 숨겨둘 것: 기술 수집 로그와 실험성 분석. 삭제하지 않고 관리·상세 분석으로 이동합니다.
- 유지할 것: ERP의 확정 거래 흐름과 PMS의 채널 수집·진단 전문 기능. 화면 통합이 모든 테이블의 물리적 합병을 뜻하지는 않습니다.

## 검토 범위와 사실 구분

| 항목 | 이번 확인 |
|---|---|
| ERP | App 라우트·Layout 메뉴 전수 목록, 생산 의뢰/수주 연결, 자금·손익, 업무 확정·비서실 집계 주요 경로 |
| PMS | App에 등록된 26개 페이지 목록, 리오더 저장, 캘린더·운영시트 동기화, 공통 API·시트 편집, 브랜드 전달 |
| 정적 검사 | ERP `npm run check` 통과, PMS `npx tsc --noEmit --incremental false` 통과 |
| 부하 기준 | 대표가 제시한 직원 25명 × 일 40건 이상 = 일 1,000건 이상 |
| 미수행 | 이번 검토에서 운영 데이터 생성, 외부 할인 적용·메일 전송, 실입출금, 법인 분리 실험, 전 탭 브라우저 재실행은 하지 않음 |

아래 '문제'는 확인한 코드에 근거합니다. '보강'은 권고 설계이며 이미 구현되었다는 뜻이 아닙니다. 모든 상세 화면의 모든 내부 함수까지 읽은 전수 코드 감사는 아닙니다.

## 1. 우선 수정이 필요한 발견

### 1) 브랜드 선택이 PMS 데이터 요청으로 전달되지 않음 — 우선

- 역할: ERP에서 선택한 LUMEN/AETALOOF의 업무를 PMS 화면에서 열어야 합니다.
- 문제: ERP `client/src/pages/PmsWorkspace.tsx`는 iframe에 `embedded`와 인증 토큰만 전달합니다. PMS `web/src/api.ts`도 브랜드 헤더를 보내지 않습니다. PMS `app.py:83`은 헤더/쿼리로 브랜드를 정하므로 이 경로에서는 기본 LUMEN으로 처리됩니다. 또한 `services/campaign_perf.py`는 ERP 기획전을 브랜드 조건 없이 조회하면서 판매는 현재 브랜드로 조회합니다.
- 조치: 화면 선택 → 요청 브랜드 → 조회 조건을 일치시키고 서버에서도 접근 가능한 브랜드를 확인합니다. 기획전 조회도 해당 브랜드로 제한합니다.
- 방치 결과: AETALOOF를 열었는데 LUMEN 데이터가 보이거나 다른 브랜드 기획전에 현재 브랜드 판매가 붙을 수 있습니다. AETALOOF 운영 개방 전 필수 조건입니다.

### 2) PMS 리오더 확정과 ERP 생산 의뢰가 다른 장부 — 우선

- 역할: 판매·재고를 바탕으로 재생산을 판단하고 실제 생산 의뢰로 넘깁니다.
- 문제: PMS `services/reorder.py:201`의 `save_order`와 `set_status`는 SQLite `reorders`만 변경합니다. ERP 브랜드 발주/수주 저장을 호출하지 않습니다. ERP `BrandOrders.tsx`는 별도로 재고·수요 기반 리오더를 계산합니다.
- 조치: 추천과 시뮬레이션은 PMS에 유지하고, 승인하면 ERP 브랜드 생산 의뢰를 한 번 생성합니다. 이후 확정 수량·납기·입고는 ERP 연결 ID로 조회합니다.
- 방치 결과: PMS에서 '확정'해도 OEM 수주함에는 없는 주문이 됩니다. 직원이 같은 주문을 다시 입력하게 됩니다.

### 3) 기획전·업로드 일정·채널 플랜의 확정 원본이 분산 — 우선

- 역할: 확정 일정이 관계 팀과 운영 화면에 같은 내용으로 보여야 합니다.
- 문제: ERP `server/work.ts:530`은 일정 확정 RPC로 ERP 캠페인을 저장합니다. PMS `web/src/CalTab.tsx:11`은 별도 `일정 목록` 시트를 읽습니다. `routes/inventory.py:659`의 채널 플랜 저장은 운영시트를 읽어 전체 시트를 교체합니다. 성과 조회 연결은 있으나 동일한 일정 원본은 아닙니다.
- 조치: ERP 일정 ID를 정본으로 하고 기획전·콘텐츠 게시·생산 마감을 유형으로 구분합니다. PMS 달력과 채널 플랜은 필요한 유형의 보기로 전환합니다. 외부 시트는 ID·출처·수정 시각으로 대조하여 가져옵니다.
- 방치 결과: 확정한 일정이 다른 달력에 없거나, 직접 고친 채널 플랜이 다음 수집에서 바뀝니다.

### 4) 대표 보고·질문 검색이 예상 사용량을 모두 반영하지 못함 — 우선

- 역할: 비서실은 대표에게 회사 전체 상황과 미결 사항을 빠짐없이 보여야 합니다.
- 문제: ERP `server/ceo.ts:208`은 최근 30일 중 최신 300건으로 미결·팀 숫자를 계산합니다. `server/work.ts:180`의 질문 근거는 최신 150건입니다. `server/agents.ts:124`는 페이지 조회로 집계 누락을 개선했지만 AI 설명 입력은 `:74`에서 팀 카드 120건만 사용합니다. 30일 이전 미결 업무도 해당 기간 조회에서 빠집니다.
- 조치: 전체 숫자는 DB 집계로 계산하고, 미결·연체는 생성일과 무관하게 조회합니다. AI는 중요 미결·관련 자료를 찾아 요약하고, 근거 ID·조회 기간·포함 건수·미반영 범위를 표시합니다. 과거 답변은 저장된 일별 요약과 원본 검색을 함께 사용합니다.
- 방치 결과: 일 1,000건이면 대표 화면의 최신 300건 밖 업무가 존재하는데도 전체 현황처럼 보고됩니다. 기록 저장과 모든 기록을 답변에 활용하는 것은 별개입니다.

### 5) '영업이익'이라는 이름과 원가 매칭이 계산 범위를 과장 — 우선

- 역할: 판매의 실제 수익성과 생산 건별 원가를 확인합니다.
- 문제: ERP `client/src/pages/ProjectPL.tsx:32`는 매출에서 공장원가·배송비·플랫폼·PG 수수료만 차감하고 화면 `:77`은 이를 영업이익으로 표시합니다. 급여·임차료·광고비 등의 포함 경로가 없습니다. 같은 품번의 첫 생산 오더를 원가로 선택할 수 있어 서로 다른 배치 단가가 섞입니다.
- 조치: 현재 값은 '판매 기여이익'으로 이름과 포함 비용을 명확히 합니다. 원가는 판매-상품-입고배치 또는 확정 재고평가 기준에 연결합니다. 생산 발주 손익과 전사 비용 포함 손익은 별도 보기로 유지합니다.
- 방치 결과: 대표가 화면 금액을 전사 영업이익으로 오해하거나, 재생산 단가가 바뀐 상품의 이익을 잘못 판단합니다.

### 6) 순유입이 양수라고 자금 상태를 '정상'으로 표시 — 우선

- 역할: 월별 지급 가능 여부와 부족 시점을 예측합니다.
- 문제: ERP `client/src/pages/CashPlan.tsx:63`은 월 유입-유출이 양수면 '정상'입니다. 기초 잔액·월중 지급 순서·최소 잔액을 반영하지 않습니다. 화면은 현재 사업 선택에 따른 필터가 없어 그룹 합산인지도 불명확합니다. 사업 선택에는 `AETALOOP` 표기 불일치가 있습니다.
- 조치: 우선 '순유입/순유출'로 표시하고 범위를 '그룹 전체' 등으로 명시합니다. 이후 기초 잔액·예정일별 누적 잔액·확정/예상·부족일을 추가합니다. 그룹과 법인/사업별 보기를 나눕니다.
- 방치 결과: 월말 유입이 있어도 월초 지급은 못 하는 상황을 '정상'으로 읽을 수 있습니다.

## 2. 함께 정비할 발견

### 7) 이전 서버 주소가 PMS 사용자 경로에 남음

- 역할: 세션 만료·로그아웃·워크스페이스 전환 시 현재 ERP/OS로 돌아갑니다.
- 문제: PMS `web/src/App.tsx`의 `ERP_URL`, 인증 실패 이동, 사용자 조회, 로그아웃은 `54-116-241-64.sslip.io` 주소를 직접 사용합니다. 현재 요청 대상인 `ameserp.kr`과 다릅니다.
- 조치: 현재 운영 ERP/OS 주소를 하나의 배포 설정에서 읽도록 통일합니다. 인증 만료·로그아웃·단독 PMS 실행을 각각 테스트합니다.
- 방치 결과: 평상시 iframe이 열려도 세션 만료나 단독 접속에서 옛 서버로 이동합니다.

### 8) 자동 수집·읽기용 시트까지 직접 편집 가능

- 역할: 직원이 수정 가능한 값과 외부 시스템의 기준 값을 구분해야 합니다.
- 문제: PMS `web/src/SheetTab.tsx:135`는 점검 가이드만 읽기 전용입니다. 채널 플랜은 서버 안내상 읽기용인데 편집 가능하며 `api_plan_update`는 전체 교체합니다. 셀 수정은 원본 행 인덱스를 전송하므로 수집 후 순서가 바뀐 상태에서 오래 열린 화면의 수정도 별도 점검 대상입니다.
- 조치: 원본 수량·판매액·외부 일정은 읽기 전용으로 하고 담당자 확인·메모·예외 조정만 별도 저장합니다. 수동 원가 같은 필요한 입력은 허용 필드로 한정합니다. 수정 키는 상품/업무 ID와 버전을 사용합니다.
- 방치 결과: 직원이 고쳤다고 생각한 값이 다음 수집에 덮어써집니다. 행 순서 변경에 대한 동시 편집 검증도 필요합니다.

### 9) 실패한 저장·조회가 성공처럼 보이거나 계속 로딩될 수 있음

- 역할: 조회·수정 결과를 직원이 믿을 수 있어야 합니다.
- 문제: PMS `web/src/api.ts:33`은 401만 예외로 처리합니다. 다른 실패 상태는 JSON으로 반환합니다. `SheetTab.tsx:87`은 저장 응답을 검사하지 않습니다. `SalesTab.tsx:20`은 요청 예외 시 로딩 해제하는 `finally`가 없습니다.
- 조치: 공통 API에서 HTTP 실패·업무 오류를 처리하고 각 작업에 저장 중/성공/실패 및 재시도 상태를 표시합니다. 로딩은 실패해도 종료합니다.
- 방치 결과: 저장 실패 후 화면 셀만 바뀌어 재조회하면 값이 되돌아오거나, 매출 조회가 무기한 기다리는 것처럼 보입니다.

### 10) 상품 마스터를 없애기보다 하나의 상품에 서로 다른 속성을 연결해야 함

- 역할: 제조 품목과 온라인 판매 상품을 같은 상품으로 추적합니다.
- 문제: ERP 품목 마스터, PMS 상품 리스트, 채널 SKU 대조가 나뉩니다. 품번이 같다는 이유만으로 생산 스타일·색상 SKU·채널 상품을 동일한 단위로 취급하면 배치 원가와 재고 연결이 틀어집니다. PMS 기획전 성과도 `styleNo`를 판매 SKU 필터로 사용하므로 매핑 검증이 필요합니다.
- 조치: 스타일 → 색상/옵션 SKU → 채널 상품 ID 매핑을 기준정보에 둡니다. 품목·상품 리스트의 중복 기본정보 입력만 제거하고 제조 사양과 판매 콘텐츠는 각 전문 화면에 남깁니다.
- 방치 결과: 서로 다른 상품이 합쳐지거나 같은 상품의 판매가 성과 집계에서 빠집니다.

### 11) '오늘'의 기본 내용과 일부 메뉴 설명이 실제 업무와 불일치

- 역할: 오늘 할 확인·승인·마감만 먼저 보여주는 직원 업무 시작점입니다.
- 문제: ERP `Layout.tsx`의 브랜드 '오늘'은 PMS '일일점검'으로 연결합니다. 현재 일일점검에는 수집 상태·설정 누락 등 기술 운영 정보가 들어갑니다. '판매·고객' 첫 화면은 채널별 매출이며, 시트형 '채널 대조' 설명은 일괄 적용까지 안내하지만 해당 화면의 액션 구성과 대조가 필요합니다.
- 조치: 오늘은 본인 대기·마감·예외에 집중하고 수집 로그는 관리로 이동합니다. 고객 분석은 판매·고객의 명시적 하위 보기로 연결합니다. 각 버튼 설명은 실제 가능한 동작까지만 안내합니다.
- 방치 결과: 직원이 필요한 업무 대신 시스템 로그를 읽고, 설명에 있는 기능을 찾느라 시간을 씁니다.

### 12) 연결되지 않은 프론트엔드 코드와 개발용 조작은 정리 후보

- 역할: 직원 화면은 운영 행동만 제공하고 한 기능의 화면 구현은 하나여야 합니다.
- 문제: PMS `Marketing.tsx`·`MarketingTab.tsx`는 등록된 App import/탭에 연결되지 않습니다. 저장소 검색상 전자는 전용 CSS 주석만, 후자는 자신의 선언만 나타납니다. App의 `TAB_TYPE`도 선언 후 사용되지 않습니다. ERP `ProjectPL.tsx`에는 로컬 정산 데이터 서버 이관 버튼이 있습니다.
- 조치: 미연결 마케팅 화면은 현재 캠페인/분석과 필요한 기능 비교 후 코드·전용 스타일 삭제 후보로 확정합니다. 사용하지 않는 React `TAB_TYPE`만 제거 대상입니다. `static/index.html`의 동명 변수는 실제 사용되어 같이 지우면 안 됩니다. 이관 버튼은 관리자 도구로 옮깁니다.
- 방치 결과: 실제 쓰지 않는 화면까지 유지보수하고 직원에게 운영과 무관한 개발 작업이 노출됩니다.

## 3. 목표 업무흐름

### 직원 업무 입력

`챗봇·사진·음성 입력 → 기존 업무/상품/거래처 찾기 → 변경안 확인 → 필요한 권한자가 확정 → 원본 업무 업데이트 → 관계 팀 알림 → 비서실 근거 데이터 갱신`

- 업무 공유·할 일은 직접 저장 가능하되, 생산 발주·금액 변경·외부 할인·전송은 행동별 승인 규칙을 유지합니다.
- AI는 제안과 초안을 만들고, 권한자 판단을 대신 '확정'했다고 쓰지 않습니다.
- 같은 문서·대화를 다시 입력하지 않습니다. 수정 요청은 기존 객체에 연결합니다.
- 읽음/확인과 승인/완료를 구분합니다. 읽었다고 생산·지급이 완료되면 안 됩니다.

### 브랜드와 OEM 거래

`PMS 수요 추천 → 브랜드 생산 의뢰 → 브랜드 발주서 → OEM 수주·납기 회신 → 자재/생산 → 출고·운송 → 브랜드 검수·입고 → 청구 근거 확정 → 양측 채권·채무 → 수금·지급 → 자금 전망`

- ERP `InboundPO.tsx`의 브랜드 발주 → OEM 생산 오더 생성과 `brandBatchId`·PO 참조·납기 회신 구조는 유지할 가치가 있습니다.
- 동일 거래를 공유하되 브랜드가 OEM의 생산 장부를 직접 수정하지 않습니다.
- 'OEM 출고', '브랜드 수령', '검수', '청구 확정'은 다른 사건입니다. 하나의 완료 체크로 합치지 않습니다.
- 후속 법인 분리는 `법인`, `사업/브랜드`, `거래 상대 법인`을 별도 기준으로 둡니다. 내부 거래 상계는 그룹 보고에만 적용하고 양측 채권·채무 기록은 보존합니다.
- 명세서 작성만으로 무조건 확정하지 않고 청구 금액·확정 주체·취소/수정 이력을 연결합니다. 계산서/외부 회계 연동은 대표가 보류한 후속 작업으로 유지합니다.

### 기획전·콘텐츠·매출

`기획전 제안 → 담당 결정 → 확정 일정 → 채널/상품/할인 연결 → 마케팅 제작 과제 → 콘텐츠 승인·게시 → 채널 실행 → 실제 판매/비용 수집 → 기획전 성과 → 다음 제안`

- 계획 확정과 외부 플랫폼 할인 적용은 분리합니다. 일정 승인만으로 쇼피파이 가격을 바꾸지 않습니다.
- 취소/기간 변경은 연관 제작 과제·일정·할인 실행 상태까지 함께 확인합니다.
- 판매 실적과 입금은 구분합니다. 매출 발생일을 현금 입금일로 그대로 넣지 않습니다.

### 비서실

`확정 업무·거래·일정·매출 → 팀 에이전트 검토 → 팀 간 질문/불일치 확인 → 대표 결정 목록과 데일리 보고 → 대표 지시 → 담당 실행 업무 → 결과 확인`

- 원형 회사 지도는 현황의 보기로 유지합니다. 지도나 대화가 별도의 업무 원본 장부가 되지 않게 합니다.
- 보고마다 숫자 출처·기준일·확정/예상·담당·원본 링크를 연결합니다.
- 대표 전용 콘솔은 직원 ERP와 별도 화면으로 유지합니다. 자동 실행은 승인 범위가 정해진 행동부터 도입합니다.

## 7. 화면 내용·용어·차트 기준

- 모든 주요 탭의 기본 구조: **확인할 것 → 처리할 것 → 완료·이력**. 관련 원본 링크와 출력/전송은 해당 건 내부에 둡니다.
- '확정'은 무엇이 확정됐는지 표시합니다: 일정 확정 / 발주 승인 / OEM 수락 / 매입 확정 / 지급 완료.
- '정상', '영업이익', '완료' 등은 실제 판단 근거와 계산 범위를 충족할 때만 사용합니다.
- '상품관리'와 '품목 마스터'는 업무 허브와 기준정보로 구분하되 직원에게 두 번 작성시키지 않습니다.
- 브랜드명은 `AETALOOF`, 금액은 통화·기간·환산 기준, 모든 수집 값은 갱신시각을 통일 표기합니다.
- 필요한 차트: 자금계획의 누적 잔액·부족 구간, 판매의 채널/기간 비교, 생산의 납기 위험, 상품의 판매-재고 추이.
- 단순 상태·금액 몇 개는 표/숫자가 더 낫습니다. 모든 탭에 장식 차트를 넣지 않습니다.
- 애니메이션은 저장 상태·업무 이동·에이전트 처리 상태에만 짧게 적용합니다. 분석 정비와 함께 전면 디자인 교체를 실행한 것은 아닙니다.
