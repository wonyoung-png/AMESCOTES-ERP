## 검증

- ERP/PMS TypeScript 검사와 운영 빌드 통과.
- TypeScript 회귀 검사 23건, PMS 안전 회귀 검사 7건 통과.
- 기존 PMS 리오더/PLC 검사 30건 통과. 기존 브랜드·행·건강·성능·상품 점검·표시·썸네일·SSO 검사 통과.
- 운영 DB RPC 회귀 검사는 BEGIN/ROLLBACK 안에서 실행하도록 준비: 중복 생성·기존 수량 보존·서버 전용 실행 권한.
- 실제 발주·할인 적용·외부 메시지·송금은 테스트로 실행하지 않음.

## 유지 / 후속

- 대표 전용 접근 제한 유지. 직원 공개와 역할별 메뉴/API 권한표는 별도 단계.
- AETALOOF 데이터 격리만 유지하며 브랜드 사업 기능 확대는 보류.
- 법인 분리 대비 OEM 생산 공급과 브랜드 의뢰·비용 책임은 기존 흐름 유지. 별도 법인 회계 원장 전체 구현을 완료한 것으로 간주하지 않음.
- 은행·회계 외부 연동, 과거 일정 일괄 이관, 외부 채널 계획 자동 확정은 보류.
- 이미지/할인/콘텐츠 등록 등 외부 실행 기능은 기존 확인 절차 유지.
- ponytail·karpathy 기준으로 변경 범위를 제한하고, graphify 관계 조회 후 실제 소스로 연결을 확인함.

## 운영 검증 상태

- 새 운영 서버 ERP/PMS 배포 완료. 배포키를 명시하도록 ERP Git 설정 정비, 이전 서비스 이미지를 복구용으로 보관.
- 운영 DB RPC 검사 PASS: 초안 원자적 저장·재시도 중복 방지·기존 수량 보존·anon 실행 금지. 검사 트랜잭션 ROLLBACK 완료.
- 서비스 건강 검사 HTTP 200, 대표 전용 `ERP_PRIVATE_MODE=true` 확인.
- Chrome 실제 로그인 화면에서 브랜드 운영 5개 메뉴 진입 확인. 상품·리오더·판매·고객·콘텐츠·운영 일정 로딩 확인.
- 기존 추천을 ERP 미리보기로 불러오는 것까지 검증. 실제 생산 의뢰 생성/발주는 브라우저에서 실행하지 않음.
- LUMEN ERP 일정 8건, AETALOOF 0건 조회. 브랜드 전환 후 iframe `brand=aetaloof` 및 다른 브랜드 일정 비노출 확인. OEM은 브랜드 선택 안내 표시.
- 자금 시나리오에서 최소 잔액 미달 날짜·상태·차트 표시 확인. 가정 입력은 저장하지 않음.
- 고객 화면의 기존 0명/100% 초과 오류 수정 후 등급 합계 7,182명·각 비율 합계 100% 확인. 금액은 자사몰 주문 기준으로 변경.

## 아직 일괄 변경하지 않은 부분

전체 검토표는 설계 방향이며 모든 항목이 자동으로 구현 완료된 것은 아니다. 접수함/업무함의 데이터 모델 통합, 법인별 거래·회계 원장 분리, 외부 운영시트 45건과 ERP 일정의 정본 대사, 과거 중복 추천 정리, 생산 납기 위험 지표는 추가 단계다. 특히 기존 추천 장부에 같은 상품·날짜·수량의 여러 행이 있어도 실제 서로 다른 의뢰인지 확인 전 삭제/자동 병합하지 않았다. 지금은 동일 추천 ID의 재시도로 발생하는 신규 중복만 차단한다.

## 잔여 작업 후속 — 업무함과 일정 대사

- 업무 피드와 증빙·접수를 `/work` 업무함의 두 탭으로 통합. 과거 `/inbox` 주소는 증빙·접수 탭으로 연결한다.
- 통합 범위는 진입점·화면·대기 숫자이며, 업무 카드와 증빙의 저장 모델 및 승인 권한은 유지한다. 읽음 처리는 전표 승인으로 취급하지 않는다.
- 접수 목록에 전체 건수와 200건 단위 페이지를 제공하고, 대기 숫자는 전체 범위에서 조회한다. 일반 직원은 기존처럼 본인 접수만 조회한다.
- 탭 전환으로 접수 수정 상태를 초기화하지 않으며, 조회 실패를 빈 정상 목록으로 표시하지 않는다.

## 비서실 운영 근거 통합 — 2026-10-09

- 대표 콘솔의 현재 운영 점검과 대표 질문에 같은 팀 감시 자료를 연결했다. 최신 조회 시각·원본 화면 링크를 제공하며, AI가 현재 근거보다 과거 팀 보고를 우선하지 않도록 구분한다.
- 생산 감시는 납기 화면과 같은 `productionRisks` 규칙을 사용한다. 입고 이력 우선, 완료 상태와 수량 불일치·납기 누락·공장 확정일 초과·전량 입고 후 상태 확인을 보고한다.
- 미수금은 정산 장부의 청구액에서 부분 수금을 차감한다. 명세표 총액을 이미 수금한 금액까지 미수금으로 보고하지 않는다.
- 당월·다음 달 자금계획은 기존 `buildMonthlyCashPlan`을 공유한다. 예상/확정·부분 지급·예상 가공비와 확정 입고비 중복 차감을 유지하며, 은행 잔고 미연동 상태에서 자금 부족을 단정하지 않는다.
- 감시 자료·팀 최신 보고를 페이지 조회한다. 조회 실패는 경고 및 판단 보류로 표시하며, 취소 업무는 오늘 완료에서 제외하고 한국 자정 경계의 완료를 포함한다.
- 디자인 준비 요청은 해당 브랜드 팀에만 보낸다. 종료일이 지났지만 준비/진행 상태인 행사는 확인 조건으로 보고하며 자동 종료하지 않는다. AETALOOF의 실제 응답을 LUMEN과 숫자가 같다는 이유로 버리지 않는다.
- AI 보고 작성 실패에도 규칙 집계·확인 조건을 남긴다. 대표 화면은 오늘 이전 보고를 표시하고 회사 지도에 현재 미결·마감·운영 감시 숫자를 사용한다.
- 검증: 서버 및 자금/업무 흐름·대표 콘솔 지도 회귀 테스트 42건 통과, 타입 검사와 빌드 통과, 대표 콘솔 인라인 스크립트 문법 검사 통과. 원본 자금계획의 11월 예상입금 385,000원이 비서실에서는 기존 만원 반올림 형식에 따라 39만원으로 표시되는 것을 확인했다.
- 범위 밖 유지: 법인별 원장 분리, 직원 개방·역할별 메뉴/API 표, 은행 자동 연동, 외부 시트 일정/중복 후보 자동 확정. 실자료 삭제·승인·전송 없음.
- 브랜드 일정 화면에 `일정 대사`를 추가. 외부 채널 계획과 ERP 일정을 읽기 전용 비교하며, 일치·기간 겹침·미등록·중복 후보·날짜 오류를 구분한다.
- 반복 헤더와 빈 행은 행사 집계에서 제외. W컨셉 국내/해외 채널을 임의 병합하지 않으며, AETALOOF 미연결 원본을 LUMEN 자료로 대체하지 않는다.
- 종료일이 지났지만 준비·진행 상태인 ERP 일정은 별도 확인 대상으로 표시한다. 대사 기능은 원본 등록·삭제·승인·할인 실행을 하지 않는다.
- ERP 검사·빌드 및 TypeScript 회귀 23건, PMS 안전/대사 회귀 12건 통과.
- 새 운영 서버 배포 후 Chrome 로그인 화면 검증: 업무함 대기 숫자 3(업무 1 + 접수 2), 두 탭 표시, 과거 `/inbox` 주소 연결 확인.
- LUMEN 운영 원본 대사 결과: 외부 행사 45건, ERP 일정 8건, ERP 미등록 43건, 기간 겹침 검토 2건, 종료일 경과 미종료 2건. 이는 등록/종료 판단이 필요한 차이이며 원본을 자동 수정하지 않았다.
- 법인 원장 분리는 대표 지시로 후순위 보류(2026-10-09). 당장은 구현하지 않으며 기존 거래 소속을 추정 변경하지 않는다.

## 잔여 작업 후속 — 중복 추천·생산 납기

- 리오더 장부에 동일 브랜드·날짜·품번·수량·공장의 중복 후보 및 비교 ID를 표시하고, 후보만 보는 필터를 추가했다. 취소건·B2B 납품은 후보에서 제외한다.
- 상태별 목록에서도 다른 상태의 비교 후보를 놓치지 않도록 전체 브랜드 장부에서 후보를 찾는다. 기존 기록·입고·상태·추천 계산값은 변경하지 않는다.
- 운영 LUMEN 리오더 82건 중 후보 22건, 7묶음 확인. Chrome 장부 필터에 정확히 22행 표시되는 것까지 검증. 후보가 실제 중복인지 별도 의뢰인지는 업무 판단 후 처리해야 한다.
- 납기 관리에 생산 납기 점검을 추가: 입고 이력 우선, 이력이 없으면 발주 기록을 사용한다. 출고를 입고로 더하지 않는다.
- 미입고 잔량과 한국 날짜로 납기 지연·7일 내 납기·공장 확정일 초과·납기 미확인·완료 상태 불일치를 분류한다. 전량 입고건은 지연 경보에서 제외하며 상태가 미완료이면 상태 확인으로 표시한다.
- OEM 작업과 브랜드 자체 작업을 구분하되, 브랜드가 OEM에 의뢰한 생산은 명시적 brand_batch_id 연결로 해당 브랜드 납기에도 포함한다. 품명이나 품번으로 소속을 추정하지 않는다.
- 운영 OEM에서 납기 지연 2건, 납기 확인 1건 표시 확인. 이는 ERP 기록 기준이며 실제 공장 진행을 대신 확인한 것은 아니다.
- ERP TypeScript 검사·빌드·회귀 27건, PMS TypeScript 빌드·안전/대사 회귀 15건, 기존 리오더/PLC 30건 통과.
- ponytail·karpathy의 최소 변경 및 원본 보호 기준 적용: 자동 병합·삭제·완료·발주 기능을 추가하지 않았다. graphify 연결 지도는 실제 소스로 검증했다.

## 잔여 작업 후속 — 브랜드 승인·수주와 일정 확정

- 브랜드 발주 작성에 대표 승인 경로를 연결했다. 승인되지 않은 의뢰는 발주서를 발행할 수 없으며, 대표 승인 권한은 서버 세션에서 다시 확인한다.
- 승인·공장/경로별 발행·OEM 수주·발주 취소를 서버 전용 DB 트랜잭션으로 처리한다. 수주 시 생산발주·수주 표시·브랜드 납기를 함께 저장하고, 일부 스타일 저장 실패는 전체 수주를 롤백한다.
- 원본 project_no·brand_batch_id·po_batch_no와 품목 시즌을 유지한다. 생산발주는 OEM 소속, 브랜드는 의뢰 원본으로 연결된다. 별도 법인 원장을 신설하거나 실거래 소속을 변경하지 않는다.

## 잔여 작업 후속 — 미지급 지급 기록·저장 실패 검증

- 지급 기록을 브라우저 누적 계산/비동기 덮어쓰기에서 서버 전용 트랜잭션으로 변경했다. DB 행 잠금과 조회 당시 지급액 비교로 다른 창의 지급 기록 덮어쓰기·오래된 재시도·초과 지급 기록을 거부한다. 이는 장부 기록이며 은행 송금 기능이 아니다.
- 예상 계획지출은 확정 전 지급 기록을 거부한다. 잘못된 금액과 존재하지 않는 미지급도 저장하지 않는다. 통신 결과가 불명확하면 최신 목록을 먼저 확인하도록 안내하며, 별도 지급 이벤트 원장/요청 ID 기반 멱등 기록을 신설하지는 않았다.
- 미지급 화면은 서버 전체 목록을 조회한다. 빈 서버 목록도 기존 캐시를 지우며, 조회 실패는 경고 및 지급 버튼 비활성화로 표시한다. 지급 성공 이후 서버 결과로 화면을 갱신하고 부분 지급 잔액을 미지급 요약에 포함한다.
- 수동 미지급 등록과 계획지출 확정은 서버 저장 후에만 성공 표시한다. 메모 수정으로 지급액/상태를 덮어쓰지 않으며, 입고 이력·불량·미지급의 기존 동기화도 반환된 DB 오류를 확인한다.
- 입고 수량·불량 수량·날짜를 검증한다. 단가 미확정으로 미지급이 생성되지 않은 입고는 미지급 생성 완료라고 안내하지 않는다.
- 검증: TypeScript 검사와 운영 빌드 통과, 서버/자금/업무 흐름 회귀 48건, 저장 실패/캐시 회귀 8조건 통과. 운영 DB 지급 회귀 11조건 통과 후 ROLLBACK했고 test_payment_ 자료 잔존 0건을 확인했다.

## 잔여 작업 후속 — 한국입고 원자적 저장

- 입고·출고 화면의 한국입고와 브랜드 생산 의뢰의 한국입고를 같은 서버 RPC로 연결했다. 발주 누적 수량/상태·입고 이력·미지급·불량 차감/재작업 기록을 한 트랜잭션으로 저장한다. 중간 저장 실패는 전체 취소되며 성공 전 브라우저 캐시를 변경하지 않는다.
- 요청 ID를 입고 팝업 동안 유지하고 서버에서 같은 ID를 직렬화한다. 동일 요청 재시도는 기존 입고·미지급·불량 결과를 반환하며, 수량/날짜/컬러/비고 등 다른 내용은 충돌로 거부한다. 재시도 중 공장 단가가 바뀌거나 지급 기록이 추가돼도 기존 미지급 금액/지급액을 재계산하거나 덮어쓰지 않는다. 입고 후 미지급 생성 여부 변경은 별도 업무이며 같은 요청 재시도로 추가 생성하지 않는다.
- 서버의 최신 총 잔량·컬러별 잔량·유효한 생산 상태·날짜·불량 수량·원화 단가를 검증한다. 이력이 없는 과거 발주 누적 수량은 버리지 않는다. 원화 공장 단가가 미확정이면 입고만 기록하고 미지급 미생성을 경고하며 통화만 보고 임의 환산하지 않는다.
- 원본 발주번호·프로젝트·공장·workspace/brand_batch_id를 변경하지 않는다. 재작업/수정 불량은 금액을 차감하지 않고 수량을 남긴다. 입고 처리로 출고 누적 수량을 변경하지 않는다. 발주→자재구매 연동은 수정하지 않았다.
- 화면 변화: 한국입고 저장 중 버튼/닫기 비활성화, 서버 저장 후 완료 안내, 미지급 및 불량 연결 안내. 이미 서버에 저장됐지만 캐시 갱신 실패 시 같은 요청 재시도를 안내한다.
- 검증: TypeScript 검사·운영 빌드, 회귀 49건, 기존 저장 실패/캐시 8조건 + 한국입고 캐시 5조건 통과. 운영 DB와 같은 스키마에서 RPC 생성과 합성 입고 15조건을 하나의 트랜잭션으로 검증하고 함수/자료 모두 ROLLBACK했다. 미지급 ID 충돌로 후속 저장을 실패시켜 발주·입고·불량이 남지 않는 것을 확인했다.

## 재고 위치 통합 — 이지어드민 담당 세션 자문 반영

- 대표 지시로 「9. MD - 이지어드민」 Codex 세션에 자문을 요청했다. 담당 세션은 국내·해외·매장이 별도 풀이고 중국 장부를 국내 가용에 더하면 안 된다고 확인했다. API stock이 이미 가용일 가능성과 기존 PMS의 stock-ready 재차감 위험도 전달했다. 이는 담당 세션의 과거 실측 근거이며 이번 작업에서 새 실대조를 수행한 결과가 아니다.
- 사이드바 중국창고 진입점을 전체 재고(`/inventory`)로 통합했다. 국내 EZ 가용·EZ 해외·한남쇼룸·신세계센텀·중국창고를 같은 화면에서 위치별 조회한다. 기존 `/china-warehouse`는 삭제하지 않고 중국 입출고 관리로 연결한다. PMS 원본/채널 할당 화면도 바로 연결한다.

- 발주 불러오기는 발주 바이어 우선, 프로젝트/브랜드를 유지한다. OEM 자동 초안과 수동 불러오기는 폐기된 salePriceKrw 대신 현재 deliveryPrice를 사용한다. 미확정 단가는 0원 초안으로 남기되 청구는 차단한다. 발주→자재 장바구니→구매 흐름은 변경하지 않았다.
- 후속 미수금 저장 실패 시 명세표가 서버에 남을 수 있다. 성공으로 표시하거나 전체 롤백했다고 말하지 않고 같은 ID·번호로 재시도하도록 안내한다. 명세표와 미수금의 원자적 RPC, OEM/3PL 출고·명세표 초안의 원자적 저장, 레거시 일괄 업로드 경로, 서버 수금 기록 원자화·번호 동시 발급은 후속 과제다. 테이블/함수/스키마 변경·실자료 발행·출고·수금·삭제는 실행하지 않았다.
- 회귀 74건·프런트 회귀 4파일(신규 명세표 저장 실패/재시도·부분 수금·중복/상태·정정 보호 포함), 타입 검사·운영 빌드 통과. 운영 PostgREST의 명세표 updated_at 및 미수금 조건 필드 조회 HTTP 200을 확인했다. 실제 로그인 후 클릭·실자료 저장 검증은 미수행이다.

## 2026-10-10 — OEM 직출고·3PL 이동 수량 분리

- 출고 요약을 OEM 직출고·3PL 이동·미분류 출고로 나눴다. 발주 출고 한도는 전체 출고 누적으로 유지하되 OEM 전량 납품에 따른 자동 명세표 초안은 OEM 직출고 이력만 기준으로 삼는다. 3PL 이동을 OEM 매출 수량으로 사용하지 않는다.
- 이력이 없는 과거 발주 누적 입고/불량/출고를 0으로 초기화하지 않는다. 출고 목적지는 추정하지 않고 미분류로 표시하며 이력과 누적 수량을 추가 합산하지 않는다. 기존 잘못 생성된 명세표는 자동 수정·삭제하지 않았다.
- 출고 처리는 입고일·입고 누적·불량·입고 상태를 새 출고일로 갱신하지 않는다. 서버 발주 저장 후 중복 업로드 없이 로컬 캐시만 교체한다. 저장 중 중복 클릭·폼 수정·닫기를 제한하며 캐시 갱신 이후 입출고 요약/이력을 다시 계산한다.
- 합성 수량 시나리오 5종(OEM/3PL 혼합, 과거 누적, 부분 이력, OEM 전량, 빈 이력)과 TypeScript 회귀 74건·프런트 회귀 5파일·타입 검사·빌드가 통과했다. Codex 본 작업자가 변경 diff와 모든 요약 호출부를 검토한 것이며 독립 리뷰나 실제 로그인 후 저장 검증은 아니다.
- 미완료: 출고 이력·발주 누적·명세표 초안 및 청구·미수금은 아직 한 DB 트랜잭션이 아니다. 다른 PC 동시 처리/네트워크 재시도 중복 방지까지 보장하지 않는다. 새 DB 함수는 프로젝트의 올리브 보고 규칙에 따라 보고 경로 확인 후 진행하며 이번 변경에 스키마 추가·실자료 출고·청구·수금은 없다.
- graphify는 shipping/statement/receivable 연결 후보를 실제 소스로 대조하는 데 사용했고 ponytail·karpathy는 신규 메뉴·원장·의존성 없이 수량 오판 경로만 수정하는 기준으로 사용했다. 법인 원장·직원 개방·은행 연동 보류 유지.

## 2026-10-10 — 출고·명세표·미수금 원자적 저장

- 입고·출고 화면의 OEM 직출고/3PL 이동을 record_order_shipment로 전환했다. 발주 행 및 요청 ID를 잠그고 출고 이력·누적·OEM 전량 자동 초안을 한 트랜잭션으로 저장한다. 실패 시 전체 롤백하며 같은 ID의 같은 요청은 기존 결과만 반환한다. 3PL 이동은 OEM 납품 완료/명세표 초안을 만들지 않는다.
